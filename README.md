# CRM Backend (Express + PostgreSQL)

This has been run end-to-end against a live Postgres instance during
development: schema creation, seed data, registration, login, ownership
scoping, and lead conversion were all verified working before delivery.

## 1. Start the database

```bash
docker compose up -d
```

This starts Postgres 15 and automatically runs `db-init/01_schema.sql` the
first time (creates the `crm` schema, all tables, indexes, and seed data).
If you ever need to reset from scratch:

```bash
docker compose down -v   # wipes the data volume
docker compose up -d     # re-initializes from db-init/
```

## 2. Configure the app

```bash
cp .env.example .env
```

Edit `.env` and set a real `JWT_SECRET` (the example value is not safe to
use anywhere beyond local testing).

## 3. Install & run

```bash
npm install
npm run dev     # auto-restarts on file changes
# or: npm start
```

Server starts on `http://localhost:4000`. Check `http://localhost:4000/health`.

## 4. Try it

```bash
# Register
curl -X POST http://localhost:4000/api/auth/register \
  -H "Content-Type: application/json" \
  -d '{"first_name":"Jane","last_name":"Doe","email":"jane@example.com","password":"secret123","role":"sales_rep"}'

# Login
curl -X POST http://localhost:4000/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"jane@example.com","password":"secret123"}'
# -> copy the "token" from the response

# Authenticated request
curl http://localhost:4000/api/accounts \
  -H "Authorization: Bearer <token>"
```

The seed data (from `db-init/01_schema.sql`) includes 3 users you can log
into directly once you set their passwords via bcrypt, or just register
fresh users through `/api/auth/register`.

## API overview

| Resource | Endpoints |
|---|---|
| Auth | `POST /api/auth/register`, `POST /api/auth/login` |
| Accounts | `GET/POST /api/accounts`, `GET/PATCH/DELETE /api/accounts/:id` |
| Contacts | `GET/POST /api/contacts` (filter: `?account_id=`), `GET/PATCH/DELETE /api/contacts/:id` |
| Opportunities | `GET/POST /api/opportunities` (filter: `?stage=`, `?account_id=`), `PATCH /api/opportunities/:id`, `PATCH /api/opportunities/:id/stage`, `DELETE /api/opportunities/:id` |
| Leads | `GET/POST /api/leads`, `PATCH /api/leads/:id`, `POST /api/leads/:id/convert` |
| Activities | `GET /api/activities?contact_id=` (or `account_id`/`opportunity_id`/`lead_id`), `POST/PATCH/DELETE /api/activities/:id` |

All routes except `/api/auth/*` require `Authorization: Bearer <token>`.

## Ownership scoping

`sales_rep` users only see records where they're the `owner_id`. `manager`
and `admin` roles see everything. This is enforced in `src/utils/scope.js`
and applied in the accounts/contacts/leads/opportunities list endpoints.

## Known gotcha (already fixed here, but worth knowing)

The seed script inserts explicit primary keys (e.g. `user_id = 1, 2, 3`).
Postgres identity columns (`GENERATED BY DEFAULT AS IDENTITY`) don't
auto-advance their sequence when you do that, so the schema script ends
with `setval(...)` calls to resync every sequence after seeding. If you
ever add more seed rows with explicit IDs, re-run those `setval` statements
or the next real INSERT will collide with a seeded row.
